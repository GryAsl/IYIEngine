# IYI Engine: Roadmap

What is deliberately missing, what is worth adding, and in what order. Read this
before adding a system, and before "fixing" something that looks unfinished, a
lot of it is unfinished on purpose.

`docs/SPEC.md` is the contract for what exists today. This file is about tomorrow.
What already shipped (and when) is in git history (`git log -- docs/DONE/ROADMAP-history.md`, removed 2026-11-20).

---

## The rule that decides everything

Add a system when a real game needs it, not when an engine "should" have it.

The whole point of this engine is that a developer can read all of it. Today that
is ~29,700 lines of C++ in 97 files, ~5,500 of which are the IYIUI subsystem.
Every addition spends that budget, and the budget is no longer small. Before
adding anything, ask in order:

1. Does raylib already do it? Then bind it thinly, do not wrap it.
2. Can it live in game code (Python, or C++ for a native game) instead of the engine? Then it
   belongs in the game, not here.
3. Does it survive hot reload? If a feature forces state into C++ that Python
   used to own, it makes reload worse, the one thing that must never regress.
4. Would removing it later be hard? Prefer the version that is easy to delete.

A feature that fails 3 is not a trade-off, it is a no.

## Known limitations (real, documented, unfixed on purpose)

### Packaging and Release: solved, with a narrow scope

Distribution exists in two forms:
1. `package.bat` produces a loose-file developer package under `dist/` with an embeddable CPython 3.14 (3.11 with `py311`), the game's files and its libraries under `game/`, and MSVC runtime DLLs (`spec/build.md` §14b).
2. The one-click release pipeline (`release.bat` / `tools/release.py` using `iyipack`) produces a commercial shipping build under `release/<Name>/` (`spec/resources.md` §18). Game scripts are compiled to bytecode (`.pyc`) and packaged alongside assets and `project.json` into an encrypted (XChaCha20-Poly1305) and compressed (DEFLATE) `game.rres` archive. The Central Directory is omitted (`cdOffset = 0`) to prevent leaking asset names; lookups use 32-bit CRC32 IDs of normalized paths. The binary is compiled with `IYI_SHIPPING_BUILD` (hot reload compiled out, packaged backend only with no disk fallback, logs routed to the per-user data root alongside saves).

What was deliberately left out:
- **Steam upload helper**: The output directory `release/<Name>/` is structured directly as a Steam depot content root. An automated SteamPipe/SteamCMD upload script was left out; build credentials and upload automation belong in external CI or publisher scripts.
- **Multiple `.rres` packs**: The release pipeline generates a single `game.rres`. Multi-pack partitioning, patch archives, and DLC mounts were omitted until games grow beyond single-archive limits.
- **Not DRM**: This architecture provides practical packaging and obfuscation, protecting code and assets from casual inspection and modification. It is an explicit non-goal to pretend this is DRM; a decryption key present in a client executable can always be recovered by a determined reverse engineer.
- **Installer / code signing**: No MSI/installer generator or code signing pipeline; output is a clean, portable directory.

### Localization: implemented, with defined font and script scope

The localization subsystem is implemented and active across the engine and UI:
- **Authoring policy:** player text updates maintain EN/TR only; all third-language
  translation/backfill requires Gry's explicit request.
- **Scope**: Flat JSON files (`assets/locales/<code>.json`), `${name}` placeholders, fallback language resolution, `__keys__` debug pseudo-language, dev hot-reloading with fallback preservation, shipping catalog (`_catalog.json`) generated by `release.py`, and direct widget binding via `loc_key` / `loc_args`.
- **Known limitations & gotchas**:
  1. **Lowercase paths**: Language codes and locale filenames must always be strictly lowercase (`zh-cn.json`, `pt-br.json`), as `ResourceStore` normalizes all paths to lowercase.
  2. **Copy-by-value `loc_args`**: Widget `loc_args` passes across pybind11 by value; you must assign a whole dict (`el.loc_args = {...}`). In-place item mutation (`el.loc_args["k"] = v`) is silently lost.
  3. **Font and script scope**: Base atlas ranges cover Basic Latin, Latin-1, Latin Extended-A and Cyrillic. A project font containing the glyphs can render CJK through sparse preloading and on-demand expansion. Complex shaping and bidirectional layout are unsupported. See [font scope](spec/localization.md#1910-font-and-glyph-coverage-scope) and [Windows IME](IME.md).
  4. **No pluralization rules or message formatting**: Does not implement complex ICU plural forms or gender rules; games requiring dynamic grammar use separate keys or format strings in Python.
  5. **CJK and Windows IME implemented (2026-10-14)**: Project fonts plus `load_font(..., glyph_text=...)` seed sparse glyphs; one private cumulative atlas per source covers new text without replacing public handles. CJK wrapping/ellipsis is UTF-8-safe, not full shaping or Unicode line breaking. Windows uses native composition/candidate UI and raylib commits; keyboard guards include the commit/cancel frame. Real CJK provider tests remain manual, and other platforms have no new native IME bridge. See [IME.md](IME.md) and SPEC section 19.10. A game's translation scope is separate from engine glyph coverage.

### Audio: implemented, with defined streaming, alias, and spatial scope

The audio subsystem is implemented in `AudioManager` and exposed under `engine.audio`:
- **Scope**: Sound effects via raylib sound aliases, named string volume buses (`master`, `sfx`, `music`, etc.) with hierarchical volume math, 2D positional spatialization (linear falloff and horizontal pan), streaming music with crossfades and track queue, and JSON persistence to `audio.json` with `project.json` defaults.
- **Known limitations & gotchas**:
  1. **Streaming format residency**: Streaming music files (`.ogg`, `.mp3`, `.flac`, `.qoa`, `.xm`, `.mod`, `.wav`) loaded from packaged resource archives (`game.rres`) require the raw file bytes to remain resident in memory (`AssetManager::m_musicBuffers`) for the duration of playback to back the streaming decoder.
  2. **Positional audio is sound effects only**: Spatialization (`PlayAt`, `set_position`, listener falloff and stereo panning) applies strictly to sound effects (`SoundInstance`). Music tracks (`engine.audio.music`) are non-spatialized stereo streams on the `"music"` bus without world coordinates or distance attenuation.
  3. **Handle lifetime after sound finishes**: Sound handles for non-looping sounds are valid only while actively playing. When a sound finishes, `AudioManager::Update(dt)` reaps the instance, calls `UnloadSoundAlias`, and erases the handle. Subsequent calls on expired handles are silent no-ops and `is_playing(h)` returns `False`. Looping sounds remain alive until explicitly stopped via `stop(h)` or `stop_all([bus])`.
  4. **Single concurrent crossfade slot**: Interrupting an in-progress fade decays the outgoing track continuously from its current factor instead of snapping to full volume. However, because there is only one outgoing stream slot, starting a third track while an outgoing fade is already active immediately displaces and stops the older outgoing stream.
  5. **Single stream per music file**: Raylib `Music` handles are cached 1:1 per file path in `AssetManager`. You cannot crossfade a track into another concurrent stream of the exact same file path; calling `music()` on the currently playing track adjusts parameters in-place.

### Steamworks: minimal bridge (`engine.steam`)

Exposes achievements, stats synchronization, and asynchronous leaderboards via Steamworks SDK 1.65+:
- **Scope**: Stats and achievements synced on initialization (`UserStatsReceived_t`), leaderboard score uploads and downloads via `CCallResult`, and clean process restart handling (`SteamAPI_RestartAppIfNecessary`) in shipping builds. If the SDK is missing at build time or `steam_app_id` is 0, the engine compiles with a safe no-op stub where `available()` is `False`.
- **Known limitations & gotchas**:
  1. **SDK 1.61+ API model**: `RequestCurrentStats` was removed by Valve; stats synchronization occurs automatically upon initialization and completes when `UserStatsReceived_t` fires for the local user. Scripts should check `engine.steam.stats_ready()` before accessing achievements.
  2. **Async handle polling**: Leaderboard operations return integer handles polled via `request_status(h)`. Results must be freed with `release(h)` to avoid leaking request records in memory.

### Fixed 30/60 Hz only

By design (`SPEC` §9). There is no generic scheduler and adding rates means
editing `Application`, which is the intended cost.

### Single scene, no serialization

A scene is a Python script that spawns actors. There is no saved scene format, no
editor, no prefabs. Games that need persistence write their own save files
(`engine.project_path()` gives you somewhere to put them).

### Two threads, no more

Since 2026-10-18 the engine runs two threads (SPEC §8a): the main thread is the render side
(window, input, GL, audio for now) and a game thread runs Python (or a native game's C++, SPEC §2c)
and every hook, one frame ahead.
Python stays on that one thread: ordinary CPython with its GIL, no free-threaded build, no
subinterpreters. Not planned: a job system, a thread pool, parallel actor updates. Possible next
step: an audio thread taking the frame packet's Audio pass (the AudioManager is already reached
only through it).
A UI thread (UI/HUD on a third thread, needs free-threaded 3.14t) was measured and dropped on
2026-11-08: about 0 to 2 % for a large rework (HR sits at the fps cap; COIN's cost is sim Python).
Reopen only when a game is game-thread bound and its UI is over ~30 % of that thread after its
sim hot paths are native.

## IYIUI Retained-Mode UI (Phase 1 & Phase 2)


A lightweight retained-mode UI subsystem embedded in the C++ runtime and bound to
`engine.ui`.

`docs/SPEC-IYIUI.md` is the authoritative contract. This section is only a
summary and a list of what IYIUI deliberately lacks. Its "Toolbox" table lists what to use before
writing layout code by hand; added 2026-11-12: `fit_height`, `wrap_children`, the type scale
(`font_role`, `canvas.text_scale`), `theme.extend`, `canvas.problems()` (live in `debug_draw`, agent
`ui_problems`), game_kit `stack` / `window`.

### Deliberately excluded

Multi-line text, selection and caret movement (`UITextInput` is single line, append at the end) · dropdowns · toggles · tree views · data
grids · tabs · docking · rich text / BBCode / HTML markup · draggable scrollbars ·
horizontal scrolling · rotated (stencil) clipping · custom UI shaders or
post-processing · CSS-style selectors or cascading · reactive/declarative UI ·
dirty-layout dependency tracking · Python callbacks stored in native objects.

### Known limitations

- **Clipping is always axis-aligned.** `BeginScissorMode` takes a screen-space
  rectangle, so a rotated element that clips uses the axis-aligned bounding box of
  its resolved rect. Stencil masks are out of scope.
- **Canvases are screen space only.** They draw in the HUD pass and are never
  transformed by a world `Camera2D`. World-space UI would need a second pass.
- **Removed UI elements are retired, not freed.** After `remove()`, `clear_children()`
  or `clear_ui()` a held Python element is dead (`alive == False`) but its memory
  stays valid and every mutator no-ops. The cost: retired subtrees live until the
  canvas dies, so heavy remove churn grows memory. Build once and show/hide; add a
  frame-boundary purge only if that ever shows up in profiling.
- **Layout cache is exact and bounded to eight variants per canvas.** Signature
  construction still walks the tree each frame; unchanged layouts skip rectangle
  resolution, while misses recompute synchronously before drawing (HR, 3,300 elements:
  about 3 ms per miss since 2026-11-14, `docs/optimization.md`). Anything moved every
  frame goes on `translation` (visual only), never `anchored_position`. A per-subtree
  cache was judged not worth its lines at that cost.

## Explicitly rejected: do not add these

From the original plan's non-goals, still rejected:

custom collision system · physics engine · pathfinding · spatial queries ·
multithreading beyond the two threads (SPEC §8a) and the `NavPlanner` worker · thread pool · job system · ECS or archetype ECS · component
dependency scheduler · entity inspector · debug UI framework · editor or visual
editor · prefab system · animation framework · scripting dependency
graph · NumPy · Numba

Reopened by the owner on 2026-10-13: a **frame profiler**. The reason: performance work on
TransportationCo needed numbers per stage and per script, and every game would rewrite the same
timers. It stays inside the rules: the engine only collects data (`Profiler.cpp`, SPEC §12.3),
draws nothing (rule 9); the on-screen table is the opt-in `libraries/profiler_overlay`.

Reopened by the owner on 2026-10-25: **pathfinding off the game thread** (`engine.NavPlanner`,
SPEC §12.3). The reason: COIN replans many units at once when a road is blocked, a bridge falls or
a house collapses, and doing that in Python on the game thread would freeze frames. It stays narrow: up to 4
search threads inside `NavPlanner` only (no general thread pool or job system), searches on snapshots so
nothing races the game, and every behaviour (drivers, walkers, doctrines) is the Python library
`libraries/nav`. Spatial queries beyond route search stay rejected.

Reopened by the owner on 2026-10-29: **native games** (games written fully in C++, SPEC §2c). The
reason: COIN's game thread costs ~20 ms per frame in the stress scene, ~16 ms of it Python
(`docs/benchmark.md`). It stays inside the rules: same two threads, one C++ implementation per
feature with Python bindings as thin calls into it, a native game is its own exe linking
`IYIEngineCore` (no DLL or plugin loading), and every other game keeps Python and hot reload.

Reopened by the owner on 2026-11-21: **multiplayer** (`libraries/net`, SPEC §25). The reason: SuperStrategy
wrote its own host-authoritative netcode (Steam only, full state every tick, a hand-written codec per
message), and every multiplayer game would write it again. It stays inside the rules: an opt-in library
behind its own build switch (`IYI_NET`), so a game that does not list it carries none of it; host-based
only (no dedicated server, anti-cheat or rollback); no new thread (it runs on the game thread next to the
Steam callbacks); one C++ implementation that `engine.net` and native games both call; polling, not
callbacks (rule 1). New dependency: ENet (§0).

If collision is needed, call raylib's collision functions. If a "manager" or a
"service" or a "factory" seems necessary, the design is wrong, go simpler.

These are rejected for *this* engine at *this* size, not forever. Reopening one
is a deliberate decision with a reason written down, not a refactor someone slips
in.

## Video and trailers

`engine.video` plays MPEG-1 + MP2 (`.mpg`) through pl_mpeg (SPEC, `Video.cpp`). IYITrailer (`tools/trailer.py`,
`Trailer.cpp`) records scripted trailers; its final encode picks a working GPU encoder (NVENC, AMF,
QSV) else libx264. See `IYITRAILER.md` and `VIDEO-ENCODING.md`. `engine.run_path()` gives a run its own
folder and agent runs never start Steam, so runs are independent and parallel-safe.

## Shipping polish: what every game gets, and what it still owes (2026-10-15)

Found while preparing Human Resources; easy to miss because none of it shows in development.

Engine handles (no game code needed):
- **No console window**: the Windows shipping exe is a GUI-subsystem app; output goes to the log.
- **Game name in Task Manager / Explorer**: `tools/release.py` writes `GameVersion.rc` from
  `project.json` `name`/`version`; `release.json` `"exe_icon"` (an `.ico`) adds the exe icon.
- **Close button / Alt+F4 can be intercepted**: `engine.set_close_intercept(True)` +
  `engine.take_close_request()` let the game play its own exit; a second close always exits.
- **`set_window_size` recentres** the window in the monitor's work area.
- **Unused assets stay out of the package**: the release keeps only assets the code names (SPEC
  "Only reachable assets are packed"); HR dropped 23 MB of 55 (Aseprite sources, store art,
  previews). A fully dynamic path needs `release.json` `"keep_assets"`.
- **A second build from one project** (a Steam demo): `release.py --config <file>` with
  `"project_overrides"` lays keys over the packaged `project.json` (name, so its own user-data
  folder; `steam_app_id`; any game key). HR: `release.demo.json`.

Each game must still do (the engine gives the tools, not the policy):
- Shrink the startup window to the monitor (`project.json` opens its own size even on a
  1366x768 laptop); HR: `game.ui.settings.fit_to_monitor()`.
- Decide what losing focus means: `engine.is_window_focused()`; HR pauses the simulation and
  ducks the music.
- Ship a real `steam_app_id` (preflight rejects 0 and 480), an `exe_icon`, and show its version
  somewhere on screen. Third-party license texts are written by `tools/release.py` (`THIRD_PARTY_NOTICES.txt`,
  2026-11-08); OpenSSL, libffi and libtommath inside the Python embed zip, `steam_api64.dll` and raylib's
  bundled libraries (miniaudio, stb) have no text on disk yet.
- Keep saves and settings under `engine.user_data_path()`, never the install folder.

## Tier 2: real features, real cost

Do these one at a time, and only with a game that needs them.

- **Actor composition.** When "base actor + one script" stops being enough, the
  next step is *not* an ECS. It is letting an actor hold a list of script paths,
  each with its own `state` bucket. That is a small change to `GameActor` and the
  hook dispatch loop, and it keeps hot reload intact.
- **Input mapping.** `engine.is_key_down(KEY_W)` scattered through scripts becomes
  painful once rebinding matters. The cheap version is a Python-side dictionary in
  the game; only move it into C++ if profiling or ergonomics demand it.
- **Sprite animation.** Best solved in Python first (a frame index in
  `actor.state` plus `draw_texture_rec`). Promote to C++ only if it turns out
  every game rewrites the same twenty lines.
- **Tilemap drawing.** Same reasoning: try Python, measure, then decide.
- **Screen-space UI beyond `screen_space`.** The two-pass split covers HUDs. Real
  widgets (buttons, sliders) should start as Python actors, not an engine system.
- **Draw ordering.** There is no z-sorting; actors draw in spawn order. If a game
  needs layers, the smallest fix is an `int Layer` on `GameActor` and a stable
  sort in the draw pass, measure before assuming it matters.

## Tier 3: infrastructure, when the engine leaves this machine

- **Cross-platform verification [IN PROGRESS, experimental].** Linux x86_64 / macOS arm64 release pipeline and a GitHub Actions matrix
  (`.github/workflows/release.yml`) exist but have not run green yet; both stay unsupported until they do. Original note: The code is written portable (platform-guarded
  Python discovery, conditional warning flags, `std::filesystem` everywhere,
  `build.sh` present) but has only ever been built with MSVC on Windows. First
  Linux build will surface small things; none of them should be architectural.
- **Bundled Python & Packaging [DONE].** `package.bat` automates standalone distribution
  by bundling `python-3.14.8-embed-amd64` (legacy `python-3.11.9-embed-amd64`), MSVC runtime DLLs, and game assets/scripts,
  with `"hot_reload": false` set in the packaged `project.json`. Python home resolution
  checks `<exe dir>\python` automatically before falling back to system paths.
- **Release mode polish [DONE].** The shipping release pipeline (`tools/release.py`, `release.bat`, `iyipack`, `IYI_SHIPPING_BUILD`) compiles out the file watcher, compiles Python scripts to bytecode, encrypts/compresses resources into `game.rres`, and enforces per-user data roots. See `docs/spec/resources.md` §18.
- **Localization Subsystem [DONE].** Flat JSON localization system (`assets/locales/<code>.json`) integrated into engine core (`LocalizationManager`, `engine.loc`) and IYIUI widgets (`loc_key`, `loc_args`). Includes fallback language chaining, `${name}` placeholders, dev-only JSON hot reloading (resilient to syntax errors), `__keys__` debug mode, shipping catalog generation (`_catalog.json`) in `tools/release.py` / `tools/iyiloc.py`, and `engine.loc` Python API. Bundled glyph coverage covers Latin, Latin-1 Supplement, Latin Extended-A, and Cyrillic (no complex shaping/RTL). See `docs/spec/localization.md` §19 and `docs/SPEC-IYIUI.md` §9c.
- **Audio Subsystem [DONE].** Retained audio manager singleton (`AudioManager`, `engine.audio`) replacing legacy flat audio functions. Includes integer sound handles with raylib `LoadSoundAlias`, named string volume buses (`master`, `sfx`, `music`, custom), 2D positional spatialization (linear falloff + stereo panning relative to listener), background music streaming with linear fades, track crossfading, music queue, and persistent bus volume storage in `audio.json` with `project.json` defaults. See `docs/spec/audio.md` §20.
- **raylib version bumps (ongoing).** The engine follows raylib's releases (SPEC §0.1). 5.5 -> 6.2 was done
  on 2026-10-20; 5.5 stays a legacy build (`build.bat rl55`, `release.py --raylib 5.5`) for the code that
  existed then. It needed three version branches (`LoadFontAtlas`, `ApplyEffectivePan`,
  `Application::ToggleFullscreen`). Not adopted yet: 6.x features, taken up when a task benefits from them.
  Next: a newer release (6.5, 7.0, ...) when it brings something worth the bump; steps in SPEC §0.1.

## Where the tricky parts are

If you are changing the engine, these are the places that will bite you. Each has
a comment block in the source explaining it.

- **`PythonRuntime.cpp`, hook dispatch.** Lifecycle functions are fetched from
  the module dict *on every call*. Caching them for speed breaks hot reload
  completely and the breakage looks like "my edits do nothing". Never cache.
- **`PythonRuntime.cpp`, reload announcement.** `NoteReloaded` is the single
  chokepoint for console output and recording into `m_reloadedScripts`. Emitting
  the reload line anywhere else starves live actors of their `Reload` hook.
- **`PythonRuntime.cpp`, reload atomicity.** A new module is built in isolation
  and installed only on full success. The failure path must leave the previous
  module installed and must still record the new mtime, or a broken file retries
  every poll and floods the console.
- **`ActorRegistry.cpp`, reload dispatch.** If a reloaded script belongs to no
  actor (a helper module or entry script), `DispatchReload` broadcasts `Reload`
  to every live actor so UI trees rebuild. Ownership checks all actors including
  `PendingDestroy` so an actor script is never mistaken for a helper.
- **`ActorRegistry.cpp`, deferred destruction.** `Destroy()` only sets a flag.
  Removal happens once per frame. Loops iterate by index against a size snapshot
  taken before the pass, so spawning mid-pass is safe. Any `for (auto& a : ...)`
  added here is a latent crash.
- **`Application.cpp`, shutdown order.** Actors die, then Python finalizes, then
  raylib resources unload, then the window closes. Reordering this frees raylib
  handles that Python may still reference, or destroys Python objects after
  finalization.
- **`Application.cpp`, fixed-step accumulators.** Two accumulators fed
  by one clamped frame delta (`FixedStep.h`) with a catch-up cap. Removing the cap lets
  one long frame spin forever; clamping each clock separately desynchronizes 60 Hz and
  30 Hz after a stall; passing the frame time instead of the fixed step silently makes
  physics frame-dependent.
- **`PythonRuntime.h`, the pimpl.** Public headers must not include `Python.h`,
  `pybind11/*`, or `nlohmann/json.hpp`. Leaking one of these multiplies compile
  time across the whole engine, which the original design brief called out
  explicitly.
- **`LocalizationManager.cpp`, hot reload fallback retention and lowercase normalization.**
  When hot-reloading a modified locale file, parsing errors must preserve the
  existing valid string dictionary rather than clearing it, and all codes/paths
  must be lowercased to match `ResourceStore` normalization. Mutating `loc_args`
  on widgets from Python copies across the boundary by value; game scripts must
  assign whole dictionaries.
- **`AudioManager.cpp`, sound alias lifecycle and music stream pumping.**
  Sound effect instances borrow wave buffers from `AssetManager` via `LoadSoundAlias`.
  All aliases must be stopped and unloaded (`UnloadSoundAlias`) before `AssetManager::UnloadAll`
  frees the base sounds during shutdown, or raylib crashes accessing freed buffers.
  Music streams require per-frame pumping via `UpdateMusicStream`; `AudioManager::Update(dt)`
  must pump both current and outgoing crossfading streams, and handle non-looping track completion
  to advance the music queue.

## Things that must stay true

Any change that breaks one of these needs a very good reason, written down.

1. Normal gameplay work requires **no C++ rebuild**.
2. Hot reload preserves actor id, name, `WorldPos`, `Active`, `Visible`, `state`,
   the scene, and game time.
3. A Python error prints a traceback and the game keeps running.
4. Public headers stay free of Python, pybind11 and JSON headers.
5. Engine and game stay separate repos; the engine contains no game-specific code.
6. The engine draws nothing of its own, no FPS counter, no debug overlay.
7. There is exactly one way to do each thing in the Python API.
